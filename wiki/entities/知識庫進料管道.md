# 知識庫進料管道

這個知識庫有四條資料進來的路徑。兩條是既有的，兩條是 2026-08-28 新增的本機工具。

## 重點

| 管道 | 進到哪 | 怎麼運作 | 狀態 |
|---|---|---|---|
| **Telegram → n8n 自動存檔** | `raw/` | 傳連結給 Telegram bot，n8n 抓網頁、Gemini 整理、推 GitHub | ⚠️ **運作中但有兩個缺陷**，見下 |
| Obsidian Web Clipper | `Clippings/` | 瀏覽器擴充功能剪網頁 | 正常 |
| YouTube 逐字稿 | `raw/youtube_<日期>_<影片ID>.md` | `tools/capture.py --youtube <網址>` | 2026-08-28 新增 |
| 截圖（含 X、限動、付費內容、**有圖的 IG／Threads 貼文**） | `raw/shot_<日期>_<序號>.md` + `raw/assets/` | `tools/capture.py --shot <圖…>`，可一次多張 | 2026-08-30 起支援多圖 |
| **電腦 Chrome 補救**（推薦） | 同上 | 跟 Claude 說「補這篇」＋貼網址，它用你電腦上已登入的 Chrome 開貼文、自動截圖、存檔、讀圖寫內容 | 2026-08-30 實測成功 |

## Telegram → n8n 管道的完整結構

**位置**：n8n 自架於 Zeabur，`https://maxyyy.zeabur.app`
**Workflow ID**：`gMt3TVBIagJGA6PG`
**查明日期**：2026-08-30

```
你在 Telegram 傳一個連結給 bot
        ↓
  Telegram Trigger        接收訊息
        ↓
  Extract URL             取出網址
        ↓
  Jina Reader             把網頁轉成純文字        ← 缺陷 A
        ↓
  Prepare Gemini Prompt   組提示詞
        ↓
  Call Gemini API         gemini-2.5-flash 整理   ← 缺陷 B
        ↓
  Build Markdown          組成 .md
        ↓
  Prepare GitHub Payload → Commit to GitHub
        ↓
  Check Result → Send Telegram Reply（回報結果給你）
        ↓
  Obsidian github-sync 外掛同步下來 → 出現在 raw/
```

> **Jina Reader** 是免費服務（`r.jina.ai`），給它網址、回傳網頁純文字。
> **關鍵限制：它只回傳文字，不回傳圖片。**

## ⚠️ 缺陷 A：Jina Reader 讀不動 Threads / IG

Threads 與 Instagram 的內容靠 JavaScript 動態產生，而且擋未登入訪客。Jina 抓到的常常是**錯誤頁**而不是貼文本身。

**造成的後果**

1. **6 篇「404 空頁」**（`threads_2026-04-29` 系列）——不是貼文被刪，是 Jina 讀不到，Gemini 收到錯誤頁的文字就照實摘要了一遍。這 6 篇已於 2026-08-30 刪除，**原始網址保留在 [[待補資料清單]]**，管道修好後可以重傳。
2. **四個月來一張圖都沒進來**。`raw/assets/` 到 2026-08-30 前都是空的。有圖的貼文（例如十大封裝技術那篇，內容整個在圖裡）等於完全漏掉。

**這條無解**——平台限制，Jina 拿不到需要登入才看得到的圖。**有圖的貼文請直接走截圖管道。**

## ⚠️ 缺陷 B：Gemini 輸出長度上限造成截斷

**15 篇裡有 10 篇斷在句子中間**，例如：

```
raw/threads_2026-05-27（桃機停車）
  …「桃機P4停車場：位於二航     ← 就這樣沒了
```

正確內容還有「限 100 名預約、要提早 20 天登記、最少停 3 天」——**最有用的部分全部掉了**。

**為什麼會這樣**：斷在句中是「輸出 token 用完」的典型特徵。`gemini-2.5-flash` 還有一個坑——它預設會先「思考」再回答，而**思考也吃輸出額度**。若上限設成 1024、思考用掉 600，真正寫出來的筆記只剩 400 就被切斷。

### 要改的地方（待確認實際設定值）

打開 n8n 的 **Call Gemini API** 節點，看 Body / JSON 裡的：

```json
"generationConfig": { "maxOutputTokens": ??? },
"thinkingConfig":   { "thinkingBudget": ??? }
```

### 三個修法（由易到難）

**1. 最快**：`maxOutputTokens` 調到 `8192`，並加上 `"thinkingConfig": {"thinkingBudget": 0}` 關掉思考，讓額度全部用在寫筆記。

**2. 更根本**：在 `Build Markdown` 節點把 **Jina Reader 抓到的原文也寫進檔案**（例如放在筆記最後的「## 原文」段落）。這樣就算摘要被截斷，原始內容還在。
→ **消化的工作是在 Obsidian 裡由 Claude 做，管道只要負責完整搬運就好**，不需要它先幫忙濃縮。

**3. 加保險**：在 `Check Result` 節點檢查 Gemini 回傳的 `finishReason`，若為 `MAX_TOKENS` 就在 Telegram 回一句「⚠️ 這篇被截斷了」。當下就知道，不用等四個月後才發現。

## 補救路徑：用電腦 Chrome 抓圖（2026-08-30 實測成功）

Jina Reader 拿不到圖，但**你電腦上的 Chrome 已經登入 Threads/IG**，可以看到完整貼文。流程：

1. 你跟 Claude 說「補這篇」並貼上網址
2. Claude 在你的 Chrome 開啟貼文 → 點開圖片放大 → 自動截圖
3. 截圖存進 `raw/assets/`，同時建立 `raw/shot_<日期>_<序號>.md`
4. Claude 直接讀圖，把內容寫進筆記

**你完全不用碰手機，也不會在相簿堆一堆截圖。**

**首次實測**：`threads_2026-07-14`（十大封裝技術）四個月前只存到殘缺片段，2026-08-30 用這條路徑完整補回整張技術總表，寫入 `raw/shot_2026-08-30_01.md` 與 [[HBM4與先進封裝]]。

### 這條路的限制（重要）

| 限制 | 說明 |
|---|---|
| **電腦要開著、要有網路** | 休眠或斷線時完全不會執行。**這不是背景自動化** |
| **要有對話** | 需要 Claude 在對話中驅動瀏覽器，不能排程 |
| 輪播圖 | 目前只能抓到第 1 張，燈箱沒有換頁按鈕（Threads 版面問題） |

### 所以兩條管道要並存

| | Telegram → n8n（雲端） | 電腦 Chrome（Claude 驅動） |
|---|---|---|
| 何時可用 | **24 小時**，手機在外面就能存 | 只有你在電腦前、且在對話中 |
| 負責 | **不漏接**——看到就先存起來 | **補齊**——把截斷內容與圖片補回來 |
| 圖片 | ❌ 拿不到 | ✅ 拿得到 |

**運作方式**：n8n 隨時捕捉 → 每日健檢自動標記哪些被截斷 → 你開電腦時說一句「補一下」，Claude 照 [[health]] 的清單批次處理。**你不用記得哪些要補。**
